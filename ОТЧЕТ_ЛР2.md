## 1 Постановка задачи

**Объект разработки:** подмножество текста на языке, близком к TypeScript — **объявления интерфейсов** вида `interface Имя { ... };` и **псевдонимы типа с объектным телом** вида `type Имя = { ... };`.

**Требования к сканеру:**

- на вход подаётся строка (текст активного документа в редакторе), допускается **многострочность**;  
- из потока символов выделяются **лексемы** в соответствии с вариантом;  
- каждая лексема получает **условный код** и описание типа;  
- символы и конструкции, не укладывающиеся в правила, оформляются как **ошибка** (код 19) с указанием позиции (строка, столбец);  
- дополнительно выполняется **проверка последовательности лексем** (автомат валидации структуры объявлений): пропуск `;`, неверный порядок ключевых слов, неизвестные «встроенные» типы и т. п. также приводят к лексемам с кодом 19 и поясняющим сообщениям.

**Требования к интеграции в GUI (приложение Yopta Code):**

- вызов анализа из меню **«Пуск»** — пункт **«Запустить Анализ кода»** (ускоритель **Ctrl+Shift+L** / **Cmd+Shift+L**);  
- вывод в таблицу столбцов: **условный код**, **тип лексемы**, **лексема**, **местоположение**;  
- щелчок по строке с ошибкой переводит курсор редактора на позицию ошибки.

**Ограничение варианта:** после `=` в `type` поддерживается только объектный тип `{ ... }`, а не выражения вроде `type T = string;`.

**Реализация:** класс `ru.nstu.yopta.TypeScriptInterfaceScanner`, модель лексемы — `ru.nstu.yopta.Lexeme`. Таблица кодов 1–22 и примеры вывода приведены в `README.md` и в javadoc сканера.

## 2 Разработка грамматики

Различают **два уровня** описания: (1) выделение лексем из символов; (2) допустимая цепочка лексем для объявлений.

### 2.1 Лексика (алфавит символов → лексемы)

Терминальный алфавит включает латинские буквы, цифры, символ `_`, разделители `{`, `}`, `;`, `:`, `[`, `]`, `=`, пробел, табуляцию, перевод строки.

Идентификатор и «слово» для последующей классификации (`type`, `interface`, `string`, …) на этапе сканирования удовлетворяют обычному правилу цепочки букв/цифр/`_`, начинающейся не с цифры. Ключевые слова и встроенные имена типов **не выделяются отдельным путём автомата** — сначала распознаётся общий лексический класс слова, затем выполняется **классификация по словарю**.

Упрощённая схема для идентификатора (БНФ):

```text
Id  → L | L Tail
Tail → L Tail | D Tail | _ Tail | ε
L   → a | b | … | z | A | … | Z
D   → 0 | 1 | … | 9
```

Одиночные разделители и пробельные фрагменты задаются переходами конечного автомата по одному символу. Пустая входная строка порождает одну лексему с **кодом 5** («пустая строка»).

### 2.2 Структура объявления (поток лексем)

На уровне уже выделенных лексем корректные фрагменты удобно описать **контекстно-свободной** грамматикой (для спецификации; в программе используется автомат с дополнительным счётчиком вложенности `{` / `}`):

```text
Program → Decl | Decl Program
Decl    → kw_interface Id { Fields } ; | kw_type Id = { Fields } ;
Fields  → ε | Field Fields
Field   → Id : Type OptArray ;
Type    → builtin_type | Id
OptArray → ε | [ ]
```

Здесь `kw_interface`, `kw_type`, `builtin_type` — терминалы-лексемы, выдаваемые сканером.

## 3 Классификация грамматики

**Лексика** (язык допустимых лексем над алфавитом исходного текста при описании без учёта контекста вложенных скобок на этапе «нарезки» токенов) относится к **регулярным (автоматным) грамматикам типа 3** по классификации Хомского: её можно распознать **детерминированным конечным автоматом** с конечным множеством состояний.

**Язык корректных объявлений** с произвольной вложенностью фигурных скобок в теле типа **не является регулярным** (согласование скобок). В реализации `TypeScriptInterfaceScanner` проверка структуры выполняется **автоматом по лексемам** с дополнительной памятью — целочисленным **`braceDepth`**, что по выразительности соответствует **контекстно-свободному** уровню (тип 2 в иерархии Хомского при строгой постановке).

Итог для формулировки на защите: *лексический уровень — автоматная (регулярная) грамматика; полное описание синтаксиса тела объявлений — КС-аспект, в коде — КА по токенам + счётчик глубины.*

## 4 Метод анализа

Реализованы **два последовательных этапа**.

1. **Сканирование (поток символов → список лексем).** Обход текста с ведением номера строки и столбца; конечный автомат с состоянием «начало лексемы», ветвь накопления идентификатора/слова, распознавание односимвольных лексем; для слов — проверка по словарю (`type`, `interface`, встроенные типы, иначе код 13).

2. **Валидация структуры.** Второй проход по списку лексем: переключатель состояний `State` (ожидание ключевого слова, имени, `=`, `{`, полей `Id : Type`, закрытие `}` и финальная `;` и др.) и учёт `braceDepth` для вложенных `{` … `}`.

## 5 Диагностика и нейтрализация синтаксических ошибок

### 5.1 Метод Айронса

Суть **метода Айронса** при нейтрализации синтаксических ошибок в общем случае сводится к следующему:

1. При обнаружении ошибки (входной символ или токен не соответствует ни одному допустимому продолжению) определяются **недостроенные кусты** дерева разбора.  
2. Формируется множество **L** — множество остаточных символов с вершин недостроенных кустов.  
3. Из входной цепочки **удаляются (пропускаются) символы**, пока префикс входа не станет допустимым продолжением для некоторого вывода из элементов **L**.  
4. Определяется, какому кусту можно «привязать» оставшуюся цепочку, чтобы продолжить разбор.

В учебниках по компиляторам метод Айронса подробно изложен для **КС-грамматик** и разбора с построением дерева.

### 5.2 Особенности реализации в Yopta Code

В данной лабораторной работе **дерево разбора в явном виде не строится**; реализована практическая стратегия **панико-режима** на автомате проверки структуры:

- при нарушении ожидаемой конструкции в потоке лексем добавляется **синтетическая лексема** с кодом **19** и текстом ошибки (например, ожидание `;`, лишняя `}` и т. д.);  
- разбор **не обрывается**: выполняется переход в состояние, позволяющее обрабатывать дальнейший ввод (включая следующее объявление `interface` / `type`);  
- для подавления «осколков» ошибочных слов используются флаги вида **`suppressMalformedWordLine`**, **`suppressMalformedTypeTailLine`** — часть последующих лексем на той же строке опускается до пробела, перевода строки или `;`.

Таким образом, **полная нейтрализация по шагам Айронса для дерева КС-разбора не реализуется**; цель — **понятная диагностика** для пользователя редактора и устойчивое продолжение выдачи лексем.

**Пункт меню «Текст»** (с подпунктами, открывающими окна с разделами отчёта по варианту, как в типовом примере для темы «Десятичные константы Pascal») **в текущей версии приложения не выделен**. Содержание практической работы (постановка задачи, грамматика, тесты, коды лексем) приведено в **файле `README.md`** и в **настоящем отчёте (`ОТЧЕТ_ЛР2.md`)**; к защите материалы могут демонстрироваться из репозитория или из вставленных в Word фрагментов отчёта.

**Панель инструментов** с рядом кнопок быстрого вызова команд меню **в текущей версии не реализована**; все перечисленные ниже действия выполняются через **основное меню** (и сочетания клавиш там, где они заданы в коде, например **Ctrl+Shift+L** / **Cmd+Shift+L** для запуска анализа кода).

По смыслу типового ТЗ перечень функций, дублируемых с панелью инструментов в примере, в приложении распределён так:

- **Файл** — создать, открыть, открыть проект, сохранить, сохранить как, автосохранение;  
- **Правка** — отменить, повторить, вырезать, копировать, вставить, удалить, выделить всё;  
- **Пуск** — запуск с отладкой, запуск без отладки, остановка, **«Запустить Анализ кода»** (запуск **лексического анализатора** по тексту активной вкладки), настройка команды запуска/отладки;  
- вызов **справки** — пункт **«Вызов справки»** меню **«Справка»**; окно **«О программе»** — пункт **«О программе»** того же меню. Справка содержит описание реализованных функций меню в объёме, заложенном в код приложения.

**Окно (область) ввода и редактирования текста** — реализовано: много вкладок, в каждой — текстовый редактор на базе RichTextFX. Команды меню **«Файл»**, **«Правка»** и настройки из **«Вид» → «Настройки»** (в т. ч. размер шрифта редактора) работают с содержимым активной области редактирования.

**Окно (область) отображения результатов работы языкового процессора** — реализовано в виде **нижней панели с вкладками**: «Терминал», «Вывод», «Сборка», **«Лексемы»**. Ввод текста в эту панель **не предусмотрен**; на вкладке **«Лексемы»** выводится **таблица** результатов лексического анализа (условный код, тип лексемы, лексема, местоположение). Остальные вкладки служат для вывода команд терминала, сборки и т. п.

### Дополнительные элементы и возможности интерфейса

- **Изменение размера шрифта** в окне редактирования и в окне вывода — через **«Вид» → «Настройки»** (размер шрифта редактора и размер шрифта вывода).  
- **Интерфейс с вкладками** — одновременная работа с несколькими текстами (несколько открытых файлов).  
- **Выбор языка интерфейса** (интернационализация) — в настройках (русский / English).  
- **Нумерация строк** в области редактирования — реализована.  
- **Открытие файла перетаскиванием** иконки файла в окно приложения — реализовано.
